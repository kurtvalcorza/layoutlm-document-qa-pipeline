## Conformance notes

- **Standalone carrier (NOTEBOOK_SPEC 2.0 §4):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/layoutlm_document_qa_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR3):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD8):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files with `local_files_only=True` and `trust_remote_code=False` through `LayoutLMForQuestionAnswering`/`AutoTokenizer`. The upstream `pytorch_model.bin` and `tf_model.h5` are not listed and not used. The notebook's only external dependencies are the pinned PyPI distributions and the Hub at the model revision; **no OCR dependency is installed** — the default path needs none, and BYOD uses a host-present Tesseract or a caller-supplied JSON.
- **Role stages:** `validate_inputs` writes `outputs/layoutlm_document_qa_input_manifest.json` with the schema (token encoding, windowing, span scoring), the ceilings, the page size and word count, the checked questions, the verdict, and one recorded rejection finding from the box-outside-page probe; `evaluation_report` writes `outputs/layoutlm_document_qa_evaluation_report.json` — `sample-sanity` with the mean `anls`, the `exact_match` rate and one entry per question (with its span score) on the synthetic form; `not-measurable` on BYOD (with what labelled data would make the task measurable).
- The default sample is a deterministic 850×1100 invoice-style form rendered in code with Pillow's bundled font, whose renderer records each word's `ImageDraw.textbbox` — the same page and boxes the smoke run used; `anls`/`exact_match` against answers you rendered yourself with perfect OCR are sanity evidence for the input contract, encoding, forward pass and span decoding, not a DocVQA metric and not an OCR-robustness measurement. The page digest depends on the Pillow build's bundled font rendering and is printed, not asserted.
- Score semantics (UNC1–UNC4): the span `score` is the product of the start and end softmax probabilities of the chosen span within its window under the model's own head — a within-page ranking signal, not a calibrated probability and never an answerability signal (the smoke run's unanswerable question still got `14 Harbour Road,` at 0.28); the notebook says so before the first answer and again in the interpretation section, and states that any rejection threshold is the deployment's to choose on labelled pages. The notebook performs no validation of its own — words, boxes, page size and questions are checked only by the pipeline's `validate_inputs`/`answer` path.
- Ceilings `MIN_IMAGE_SIDE` (1), `MAX_IMAGE_SIDE` (10000), `MAX_WORDS` (2000), `MAX_QUESTION_CHARS` (256), `MAX_SEQ_LEN` (512), `DOC_STRIDE` (128), `MAX_ANSWER_TOKENS` (15) and `BOX_GRID` (1000) are printed before the model runs.
- CPU is documented as more than adequate (card-measured 5.1 s load, 0.11–0.29 s per question on the 73-word form; 0.47 s for a 657-word page answered across 4 windows).
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
